## 어떤 문제인가

[병합 정렬](#/algo/merge-sort)은 "쪼갠 뒤 **합칠 때** 일한다". 쪼개는 건 그냥 반으로 자르면 되고,
대신 합치기에 O(n) 과 추가 배열이 든다.

반대로 해 보면 어떨까?

> **쪼갤 때 제대로 일해 두면, 합칠 때는 아무것도 안 해도 되지 않을까?**

기준값 하나를 정해서 "그보다 작은 것들"과 "큰 것들"로 갈라 놓으면,
왼쪽을 정렬하고 오른쪽을 정렬한 뒤 그냥 **이어 붙이기만** 하면 된다.
합치기가 공짜이므로 추가 배열도 필요 없다.

## 손으로 해보기

기준값을 **피벗(pivot)** 이라고 부른다. 여기서는 **맨 뒤 원소**를 피벗으로 쓴다.

`[5, 2, 9, 1, 5, 6]` — 피벗은 마지막 `6`.

### 목표

```
[ 6보다 작은 것들 ] 6 [ 6보다 크거나 같은 것들 ]
```

이 모양을 만드는 것이 **분할(partition)** 이다.

### 분할하는 법

경계선 하나를 들고 다닌다. `i` 는 **"피벗보다 작은 값들이 놓일 다음 자리"** 다.
`j` 로 왼쪽부터 훑으면서, 작은 값을 만날 때마다 경계 `i` 로 끌어온다.

```
피벗 = 6,  i = 0

j=0: a[0]=5 < 6 → i 자리로 끌어온다 (자기 자신) → i=1
     [5] 2 9 1 5 | 6
      ↑i

j=1: a[1]=2 < 6 → i=1 자리로 (자기 자신) → i=2
     [5 2] 9 1 5 | 6
        ↑i

j=2: a[2]=9 ≥ 6 → 그냥 지나간다
     [5 2] 9 1 5 | 6

j=3: a[3]=1 < 6 → i=2 자리(9)와 맞바꾼다 → i=3
     [5 2 1] 9 5 | 6
           ↑i

j=4: a[4]=5 < 6 → i=3 자리(9)와 맞바꾼다 → i=4
     [5 2 1 5] 9 | 6
             ↑i

훑기 끝. 마지막으로 피벗을 경계 자리로 옮긴다.
     [5 2 1 5] 6 [9]
               ↑ 6 이 최종 위치에 확정!
```

**피벗 `6` 은 이제 영원히 이 자리다.** 왼쪽은 전부 6보다 작고, 오른쪽은 전부 6 이상이니까.

### 재귀

이제 `[5, 2, 1, 5]` 와 `[9]` 를 각각 같은 방법으로 정렬하면 끝이다.
`6` 은 이미 확정이므로 **다시 건드리지 않는다.**

```
[5 2 1 5] 6 [9]
    ↓        ↓
정렬        정렬
    ↓        ↓
[1 2 5 5] 6 [9]   ← 그냥 이어 붙이면 완성. 합치는 일이 없다!
```

## 아이디어 쌓기

### 1단계 — 피벗 하나를 확정시킨다

분할 한 번이면 피벗의 최종 위치가 정해진다. **정렬 문제 하나가 두 개의 더 작은 문제로 줄고,
그 사이의 원소 하나는 완전히 해결된다.**

### 2단계 — 경계 `i` 를 유지한다

분할 도중 배열은 항상 이런 모습이다.

```
[ 피벗보다 작은 것들 | 피벗 이상인 것들 | 아직 안 본 것들 | 피벗 ]
                    ↑i                ↑j
```

- `a[j] ≥ 피벗` → 가운데 구간이 한 칸 늘어난다. `j` 만 전진.
- `a[j] < 피벗` → `a[i]` 와 맞바꾼다. `a[i]` 에는 피벗 이상인 값이 있었으므로,
  교환하면 작은 값이 왼쪽 구간에 들어가고 큰 값은 가운데로 간다. `i`, `j` 둘 다 전진.

### 3단계 — 마지막에 피벗을 제자리로

훑기가 끝나면 `a[i]` 는 "피벗 이상인 것들"의 첫 칸이다. 여기와 피벗을 바꾸면
피벗이 정확히 두 구간 사이에 놓인다.

### 4단계 — 양쪽을 재귀, 피벗은 제외

```
quickSort(lo, i-1)   ← 피벗보다 작은 쪽
quickSort(i+1, hi)   ← 피벗 이상인 쪽
```

`i` 를 뺐기 때문에 **문제 크기가 반드시 1 이상 줄어든다.** 이게 재귀가 끝나는 이유다.

## 코드로 옮기기

```cpp
void quickSort(vector<int>& a, int lo, int hi) {
    if (lo >= hi) return;                     // ← 0~1칸이면 이미 정렬됨
    int pivot = a[hi];                        // ← 맨 뒤를 피벗으로
    int i = lo;                               // ← 2단계: 경계
    for (int j = lo; j < hi; j++) {
        if (a[j] < pivot) {                   // ← 작은 값을 발견
            swap(a[i], a[j]);                 //    경계로 끌어온다
            i++;                              //    경계를 한 칸 넓힌다
        }
    }
    swap(a[i], a[hi]);                        // ← 3단계: 피벗을 제자리로
    quickSort(a, lo, i - 1);                  // ← 4단계: 왼쪽
    quickSort(a, i + 1, hi);                  //          오른쪽 (i 는 제외!)
}
```

| 줄 | 손으로 한 것 |
|---|---|
| `int pivot = a[hi]` | 맨 뒤를 기준으로 삼는다 |
| `int i = lo` | 경계를 왼쪽 끝에 둔다 |
| `if (a[j] < pivot)` | 작은 값인가? |
| `swap(a[i], a[j]); i++` | 경계로 끌어오고 경계를 넓힌다 |
| `swap(a[i], a[hi])` | 피벗을 두 구간 사이에 꽂는다 |

## 자주 하는 실수

**재귀에 `i` 를 포함시킨다.** `quickSort(a, lo, i)` 라고 쓰면 구간이 안 줄어들어
**무한 재귀**에 빠진다. 피벗은 이미 확정이니 반드시 빼야 한다.

**`j < hi` 를 `j <= hi` 로 쓴다.** 피벗 자신(`a[hi]`)까지 비교하게 되어 경계가 어긋난다.

**정렬된 배열을 넣고 왜 느린지 모른다.** 이게 퀵 정렬의 가장 유명한 함정이다.
`[1,2,3,4,5,6]` 에서 피벗은 항상 `6` — 가장 큰 값이다. 그러면 분할이 이렇게 된다.

```
[1 2 3 4 5] 6      ← 왼쪽 5칸, 오른쪽 0칸
[1 2 3 4] 5        ← 왼쪽 4칸, 오른쪽 0칸
...
```

한 번에 하나씩만 줄어들어 `n` 번 재귀하고, 매번 `n` 칸을 훑는다 → **O(n²)**.
반으로 갈라지지 않으면 빠를 이유가 사라진다.

실전에서는 **피벗을 무작위로 고르거나** 세 값의 중앙값을 쓴다. 다만 이 페이지의 생성기는
"같은 입력 → 같은 트레이스"를 지켜야 해서 무작위를 쓰지 않는다. 덕분에 최악의 동작을
직접 관찰할 수 있다.

**값이 같은 원소의 순서가 바뀐다.** `swap` 이 멀리 떨어진 두 원소를 맞바꾸기 때문에
어쩔 수 없다. 안정성이 필요하면 [병합 정렬](#/algo/merge-sort)을 쓴다.

## 스스로 확인하기

1. **`1 2 3 4 5 6` 을 넣고 스텝 수를 보자.** 그다음 `5 2 9 1 5 6` 을 넣어 비교해 보자.
   같은 길이인데 스텝 수가 크게 다르다 — 피벗 선택의 위력이다.
2. **피벗이 초록으로 확정되는 순간**을 찾아보자. 한 번 확정된 칸은 다시 움직이지 않는다.
3. `Randomize` 를 여러 번 눌러 보자. 운이 좋으면(반씩 갈라지면) 스텝이 확 줄어든다.
4. 같은 입력을 [병합 정렬](#/algo/merge-sort)에도 넣어 보자. 병합 정렬은 입력과 무관하게
   스텝 수가 일정하다.
