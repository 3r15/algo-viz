## 어떤 문제인가

우리가 쓰는 수식은 **중위 표기법**이다 — 연산자가 두 숫자 **사이**에 온다.

```
3 + 4 × 5
```

이걸 계산하려면 `×` 를 `+` 보다 먼저 해야 한다(우선순위). `(3 + 4) × 5` 라면 괄호 때문에
순서가 또 달라진다. **우선순위와 괄호**를 따지는 것이 은근히 복잡하다.

**후위 표기법**(RPN)은 연산자를 숫자 **뒤**에 놓는다.

```
중위:  3 + 4 × 5
후위:  3 4 5 × +          →  4×5 를 먼저, 그다음 3+20
```

```
중위:  (3 + 4) × 5
후위:  3 4 + 5 ×
```

**후위식에는 괄호가 없고 우선순위도 없다.** 쓰인 순서가 곧 계산 순서다.
그래서 계산기와 컴파일러가 내부적으로 이 형태를 쓴다.

> 후위식을 왼쪽부터 한 번 훑어 계산하려면, 무엇을 기억하고 있어야 할까?

## 손으로 해보기

기본 입력 `3 4 + 5 *` 로 끝까지 가 보자. 이것은 중위식 `(3 + 4) × 5` 다.

### 숫자를 기억하는 그릇

왼쪽부터 읽는다. 숫자를 만나면 아직 쓸 때가 아니다 — **기억해 둔다.**
연산자를 만나면 **방금 기억한 두 숫자**를 꺼내 계산한다.

"가장 최근에 넣은 것을 가장 먼저 꺼낸다" — 또 **스택**이다.

### 왼쪽부터 훑는다

**`3`** — 숫자. 스택에 넣는다.

```
스택:  3
```

**`4`** — 숫자. 넣는다.

```
스택:  3  4        ← 맨 위가 4
```

**`+`** — 연산자. 맨 위 **둘**을 꺼낸다.

```
오른쪽 = 4 (나중에 넣은 것),  왼쪽 = 3 (먼저 넣은 것)
3 + 4 = 7
결과 7 을 도로 넣는다

스택:  7           ← 두 값이 하나로 줄었다
```

**`5`** — 숫자. 넣는다.

```
스택:  7  5
```

**`*`** — 연산자. 맨 위 둘을 꺼낸다.

```
오른쪽 = 5,  왼쪽 = 7
7 × 5 = 35
결과 35 를 도로 넣는다

스택:  35
```

### 끝났다 — 스택에 하나만 남는다

문자열을 다 읽었고 스택에 **정확히 하나** 남았다. 그것이 답이다 → **35**.

검산: `(3 + 4) × 5 = 35`. ✓

### 순서가 왜 중요한가

`-` 나 `/` 처럼 **순서가 있는 연산**에서는 어느 쪽이 왼쪽인지가 결정적이다.

```
후위:  10 3 -
꺼낸 순서: 오른쪽 = 3, 왼쪽 = 10
계산:  10 − 3 = 7        (3 − 10 = −7 이 아니다!)
```

**나중에 넣은 것이 오른쪽 피연산자**다. 스택에서 먼저 나오는 것(top)이 뒤쪽이기 때문이다.
이걸 뒤집으면 뺄셈·나눗셈이 전부 틀린다.

### 계산 순서가 이미 정해져 있다

`3 4 + 5 *` 를 보면, `+` 가 `*` 보다 **앞에 쓰여** 있다. 그래서 `+` 가 먼저 실행된다.
`(3 + 4)` 를 먼저 하라는 괄호가 **표기 순서에 녹아 있다.** 이것이 후위식에 괄호가 필요 없는 이유다.

## 아이디어 쌓기

### 1단계 — 숫자는 미뤄 두고, 연산자에서 쓴다

숫자를 만난 시점에는 어떤 연산에 쓰일지 모른다. **기억해 두었다가** 연산자가 올 때 꺼낸다.

### 2단계 — 스택이 "대기 중인 값" 을 담는다

연산자는 항상 **가장 최근 두 값**을 쓴다. LIFO 가 정확히 맞는다.

### 3단계 — 연산자 = pop 둘, 계산, push 하나

```
연산자를 만나면:
    b = pop()      ← 오른쪽 (나중 것)
    a = pop()      ← 왼쪽 (먼저 것)
    push(a 연산 b)
```

**두 값이 하나로 줄어든다.** 이 축소가 반복되며 식 전체가 값 하나로 접힌다.

### 4단계 — 순서를 지킨다

`b` 를 먼저 꺼내는데 그것이 **오른쪽**이다. `a - b`, `a / b` 처럼 써야 한다.
`b - a` 로 쓰면 뺄셈·나눗셈이 뒤집힌다.

### 5단계 — 끝에 하나만 남아야 한다

올바른 후위식이면 마지막에 스택 크기가 정확히 1이다. 그것이 답이다.
2개 이상 남거나(피연산자 과다) 연산 중 스택이 부족하면(피연산자 부족) 잘못된 식이다.

## 코드로 옮기기

```cpp
int evalRPN(vector<string>& tokens) {
    stack<int> st;
    for (string& t : tokens) {
        if (isOperator(t)) {
            int b = st.top(); st.pop();       // ← 4단계: 나중 것이 오른쪽
            int a = st.top(); st.pop();       //    먼저 것이 왼쪽
            st.push(apply(a, t, b));          // ← 3단계: 계산해 도로 넣는다
        } else {
            st.push(stoi(t));                 // ← 1단계: 숫자는 쌓는다
        }
    }
    return st.top();                          // ← 5단계: 마지막 하나가 답
}
```

**`b` 를 먼저 꺼낸다.** 스택은 나중에 넣은 것을 먼저 주므로, 먼저 나오는 `b` 가 오른쪽 피연산자다.
`apply(a, t, b)` 의 인자 순서(`a` 왼쪽, `b` 오른쪽)를 지켜야 한다.

## 자주 하는 실수

**두 피연산자의 순서를 뒤집는다.** `a = pop(); b = pop();` 로 쓰면 `a` 가 오른쪽이 되어
`10 3 -` 이 `3 − 10 = −7` 이 된다. **먼저 꺼낸 것이 오른쪽**임을 기억하자.

**스택 크기를 검사하지 않는다.** `3 +` 처럼 피연산자가 부족한 식에서 빈 스택에 `top()` 을
부르면 죽는다. 연산자 처리 전에 `st.size() >= 2` 를 확인하는 것이 안전하다.

**끝에서 스택이 1인지 안 본다.** `3 4` (연산자 없음)는 스택에 둘이 남는다.
`return st.top()` 만 하면 `4` 를 답으로 내는데, 사실은 **잘못된 식**이다.

**0 으로 나누기를 안 막는다.** `5 0 /` 는 런타임 오류다. `/` 에서 오른쪽이 0인지 확인해야 한다.

**중위식을 그대로 넣는다.** `3 + 4` 는 후위식이 아니다. 이 알고리즘은 **이미 후위로 변환된**
식을 받는다. 중위 → 후위 변환은 별도 단계(션팅 야드)다.

## 스스로 확인하기

1. **`+` 스텝**(3~4)을 보자. 스택의 `3 4` 두 칸이 계산 후 `7` 한 칸으로 **줄어든다.**
2. **설명줄의 "오른쪽 = 4, 왼쪽 = 3"** 을 보자. 나중에 넣은 4가 오른쪽이다.
3. **매 연산에서 스택이 한 칸씩 짧아지는 것**을 보자. `+`, `*` 를 거치며 3칸 → … → 1칸.
4. 입력을 `10 2 /` 로 바꿔 보자. `10 / 2 = 5` 다. 순서를 뒤집으면 `2 / 10 = 0` 이 되니
   설명줄의 왼쪽·오른쪽을 확인하자.
5. 입력을 `5 1 2 + 4 * + 3 -` 로 바꿔 보자. 이것은 `5 + (1+2)×4 − 3 = 14` 다.
   스택이 최대 몇 칸까지 쌓이는지 세어 보자.
6. 입력을 `3 +` 로 바꿔 보자. 피연산자가 부족해 **즉시 실패**한다.
7. 입력을 `4 5` 로 바꿔 보자. 연산자가 없어 끝에 **두 칸이 남아** 실패한다.

아래 **깊이 보기**에서는 스택 크기가 왜 항상 "대기 중인 값의 수" 인지 불변식으로 정리하고,
중위식을 후위로 바꾸는 션팅 야드 알고리즘과 컴파일러의 표현식 처리로 이어지는 확장을 다룬다.
