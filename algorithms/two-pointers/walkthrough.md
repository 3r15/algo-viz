## 어떤 문제인가

정렬된 배열에서 **합이 정확히 `target` 인 두 수**를 찾고 싶다.

```
a = [1, 2, 3, 5, 5, 6, 8, 9]        target = 11
```

가장 단순한 방법은 **모든 쌍을 다 보는 것**이다.

```
(1,2) (1,3) (1,5) … (8,9)      쌍이 n(n-1)/2 = 28개
```

`n` 이 1만이면 5천만 쌍. `n` 이 10만이면 50억 쌍이다.

> 정렬돼 있다는 사실을 쓰면, **쌍 하나를 보고 여러 쌍을 한꺼번에 버릴 수 있다.**

## 손으로 해보기

기본 입력 `5 2 9 1 5 6 3 8 11` — 마지막 `11` 이 목표 합, 앞은 배열이다.
배열은 자동으로 정렬해서 쓴다.

```
정렬 후:  a = [1, 2, 3, 5, 5, 6, 8, 9]
          idx    0  1  2  3  4  5  6  7
target = 11
```

### 양 끝에서 시작한다

포인터 둘을 **가장 작은 수**와 **가장 가장 큰 수**에 놓는다.

```
lo = 0 (값 1)                    hi = 7 (값 9)
```

### 1번째 — 합이 부족하다

```
a[0] + a[7] = 1 + 9 = 10  <  11
```

여기서 결정적인 추론이 나온다. `9` 는 **남은 것 중 가장 큰 수**다.
그런데 `1` 은 가장 큰 수와 짝지어도 11에 못 미친다.

> `1` 을 쓰는 어떤 쌍도 11이 될 수 없다.

`1` 과 짝지을 수 있는 상대는 `a[1..7]` 인데, 그중 최대인 `9` 로도 부족하니 나머지는 더 부족하다.
**`1` 을 쓰는 쌍 7개가 한 번에 사라졌다.**

```
[1,| 2, 3, 5, 5, 6, 8, 9]
 ↑ 버림                        lo = 1
```

### 2번째 — 맞았다

```
a[1] + a[7] = 2 + 9 = 11  ==  11        찾았다!
```

**쌍을 2번 보고 끝났다.** 전부 보면 28번이었다.

### 넘칠 때는 반대쪽

`target = 8` 로 해 보자.

```
lo=0 hi=7:  1 + 9 = 10 > 8
```

이번엔 넘친다. 대칭으로 생각한다. `1` 은 **남은 것 중 가장 작은 수**인데,
그것과 짝지어도 `9` 는 넘친다.

> `9` 를 쓰는 어떤 쌍도 8이 될 수 없다.

```
[1, 2, 3, 5, 5, 6, 8, |9]
                   버림 ↑      hi = 6

lo=0 hi=6:  1 + 8 = 9  > 8   →  8 버림.  hi = 5
lo=0 hi=5:  1 + 6 = 7  < 8   →  1 버림.  lo = 1
lo=1 hi=5:  2 + 6 = 8  ==     찾았다!
```

**부족하면 왼쪽을 오른쪽으로, 넘치면 오른쪽을 왼쪽으로.** 규칙은 이 한 줄이다.

### 없으면 어떻게 끝나나

`target = 100` 이면 항상 부족해서 `lo` 만 계속 오른쪽으로 간다.

```
lo=0..6 까지 올라가고  lo == hi 가 되면 멈춘다  →  없다
```

두 포인터가 만나면 후보가 다 떨어진 것이다.

### 왜 O(n) 인가

매 단계에서 `lo` 가 오르거나 `hi` 가 내려간다 — **반드시 하나가 한 칸 움직인다.**
둘 사이 거리는 처음 `n-1` 이고 매번 최소 1 줄어드니, 단계 수가 `n-1` 을 넘을 수 없다.

```
쌍이 n²/2 개인데 그중 최대 n 개만 본다
```

## 아이디어 쌓기

### 1단계 — 정렬이 "버려도 되는 이유" 를 준다

`a[lo]` 가 **남은 최댓값**과 짝지어도 부족하면, `a[lo]` 는 영원히 쓸모없다.
이 판정에 정렬이 필요하다. 정렬돼 있지 않으면 "남은 최댓값" 이 `a[hi]` 라는 보장이 없다.

### 2단계 — 양 끝에서 마주 본다

한쪽 끝에서만 출발하면 이 추론이 성립하지 않는다.
**한쪽은 가장 작은 것, 한쪽은 가장 큰 것**이어야 "최대와 짝지어도 부족" 이라는 판정이 가능하다.

### 3단계 — 한 번에 한쪽만 움직인다

```
sum < target  →  lo++      (합을 키운다)
sum > target  →  hi--      (합을 줄인다)
sum == target →  답
```

**둘을 동시에 움직이면 안 된다.** 그러면 사이에 있는 쌍을 근거 없이 건너뛴다.

### 4단계 — 만나면 끝

`lo == hi` 는 같은 원소를 두 번 쓰는 것이라 쌍이 아니다. 그래서 조건이 `lo < hi` 다.

## 코드로 옮기기

```cpp
pair<int,int> twoSum(vector<int>& a, int target) {
    int lo = 0, hi = a.size() - 1;      // ← 2단계: 양 끝에서
    while (lo < hi) {                   // ← 4단계: 만나기 전까지
        int sum = a[lo] + a[hi];
        if (sum == target) return {lo, hi};
        if (sum < target) lo++;         // ← 3단계: 한쪽만
        else              hi--;
    }
    return {-1, -1};
}
```

반복문 한 개, 변수 세 개. **정렬만 되어 있으면** 이게 전부다.

정렬이 안 돼 있다면 정렬 비용 `O(n log n)` 이 붙는다. 그럴 때는 해시 테이블로
`O(n)` 에 푸는 방법이 더 낫다 — 대신 정렬이 주는 다른 이득(중복 제거, 세 수의 합 확장)은 잃는다.

## 자주 하는 실수

**정렬을 안 하고 쓴다.** 1단계의 추론이 무너진다. 답이 있어도 못 찾고, **틀렸다는 신호가 없다.**

**`while (lo <= hi)`** 로 쓴다. `lo == hi` 면 같은 원소를 두 번 쓰는 셈이다.
`target` 이 어떤 원소의 두 배일 때 잘못된 답이 나온다 — `[3]` 에서 `target=6` 이 "찾음" 이 된다.

**둘을 같이 움직인다.** `lo++; hi--;` 로 쓰면 건너뛴 쌍 중에 답이 있을 수 있다.

**`sum == target` 검사를 마지막에 둔다.**

```cpp
if (sum < target) lo++;
else if (sum > target) hi--;
else return {lo, hi};      // 이렇게 써도 되지만
```

동작은 같다. 다만 `<`, `>` 만 쓰고 `==` 를 빼먹으면 무한 루프가 된다.

**오버플로** — `a[lo] + a[hi]` 가 `int` 를 넘칠 수 있다. 값이 크면 `long long` 을 쓰자.

**같은 원소를 두 번 쓰는 문제와 헷갈린다.** "한 원소를 두 번 써도 된다" 는 문제라면
조건이 `lo <= hi` 가 된다. 문제 설명을 확인하자.

## 스스로 확인하기

1. **양쪽에서 회색으로 죽는 구간**을 보자. 한 단계에 한쪽만 한 칸 준다.
2. **설명줄의 근거**를 읽어 보자. "남은 가장 큰 수와 짝지어도 모자라니 이 수를 쓰는 쌍은 전부 버린다" —
   이 문장이 알고리즘의 전부다.
3. 마지막 스텝의 "쌍을 N번만 봤다(전부 보면 28번)" 를 확인하자.
4. 입력을 `1 2 3 4 5 6 7 8 100` 으로 바꿔 보자. 없는 합이라 `lo` 만 계속 오르고,
   두 포인터가 만나 끝난다.
5. 입력을 `1 2 3 4 5 6 7 8 3` 으로 바꿔 보자 — 답이 `1+2` 다.
   `hi` 가 계속 내려오면서 오른쪽이 통째로 죽는다.
6. 입력을 `7 7 14` 로 넣어 보자. 값이 같은 두 원소로 답이 된다 — `lo < hi` 라 유효한 쌍이다.
7. 입력을 `7 14` 로 넣어 보자. 원소가 하나뿐이라 쌍이 없다. `lo < hi` 가 처음부터 거짓이다.

아래 **깊이 보기**에서는 "버려도 안전하다" 를 불변식으로 증명하고,
세 수의 합·구간 합·정렬된 두 배열 병합 등으로 이 골격이 어떻게 확장되는지 다룬다.
