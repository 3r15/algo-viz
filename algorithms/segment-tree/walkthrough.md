## 어떤 문제인가

배열이 있고 두 가지 요청이 번갈아 들어온다.

```
질의:  "3번부터 7번까지 다 더하면 얼마?"
갱신:  "5번 값을 9로 바꿔라"
```

### 단순한 두 방법

**방법 A — 그냥 배열**

```
질의: 3번부터 7번까지 훑어서 더한다      → O(n)   느리다
갱신: a[5] = 9                          → O(1)   빠르다
```

**방법 B — 누적 합을 미리 계산**

```
질의: sum[7] - sum[2]                   → O(1)   빠르다
갱신: 5번이 바뀌면 sum[5..n] 전부 수정  → O(n)   느리다
```

**둘 다 한쪽이 O(n) 이다.** 질의와 갱신이 각각 10만 번씩 들어오면 100억 번 연산이다.

> 질의와 갱신을 **둘 다 빠르게** 할 수는 없을까?

## 손으로 해보기

### 아이디어: 미리 합쳐 둔 조각들

`a = [5, 2, 9, 1, 5, 6, 3, 8]` 을 보자. 구간 합을 **미리 계산해 둔 조각들**로 만들어 놓자.
단, 모든 구간이 아니라 **반씩 쪼갠 구간들만.**

```
                    [0..8) = 39
                   /            \
          [0..4) = 17          [4..8) = 22
          /        \            /        \
    [0..2)=7   [2..4)=10   [4..6)=11  [6..8)=11
     /   \      /   \       /   \      /   \
    5     2    9     1     5     6    3     8
```

맨 아래가 원래 배열이고, 위로 갈수록 **두 자식을 합친 값**이다.
이게 **세그먼트 트리**다.

### 질의: [1, 7) 의 합은?

인덱스 1부터 6까지, 즉 `2+9+1+5+6 = 23` 이어야 한다.

트리에서 **딱 맞는 조각들**을 골라 보자.

```
[1,7) 를 덮으려면:
   [1,2) = 2        ← 리프 하나
   [2,4) = 10       ← 한 층 위 조각
   [4,6) = 11       ← 한 층 위 조각
   [6,7) = 3        ← 리프 하나
   합 = 2 + 10 + 11 + 3 = 26
```

잠깐, 26이 아니라 23이어야 하는데? 다시 세어 보자.
`a[1..6] = 2, 9, 1, 5, 6` → `2+9+1+5+6 = 23` … 아, `[6,7) = 3` 은 `a[6]` 이라 범위 밖이다.
`[1,7)` 은 인덱스 1~6이니 `a[6]=3` 도 포함이다. `2+9+1+5+6+3 = 26` 이 맞다.

핵심은 이것이다.

> **구간 크기가 아무리 커도, 조각 4개면 덮였다.**
> 배열을 하나씩 훑으면 6번인데, 트리 조각으로는 4번이다. `n` 이 커지면 차이가 벌어진다.

### 갱신: a[4] 를 1로 바꾸면?

바뀐 값의 영향을 받는 조각은 **그 리프에서 루트까지 올라가는 길 위의 것들뿐**이다.

```
                    [0..8)  ← 고쳐야 함
                   /       \
          [0..4)          [4..8)  ← 고쳐야 함
                          /      \
                   [4..6)  ← 고쳐야 함
                   /    \
                  5      6
                  ↑ 여기가 바뀜
```

8개짜리 배열에서 **3칸만** 고치면 된다. 나머지 조각은 `a[4]` 를 포함하지 않으니 그대로다.

## 아이디어 쌓기

### 1단계 — 배열로 트리를 저장한다

포인터 없이 배열 하나로 이진 트리를 담을 수 있다.

```
t[1]       = 루트
t[2i]      = i 의 왼쪽 자식
t[2i + 1]  = i 의 오른쪽 자식
```

리프 개수를 2의 거듭제곱 `sz` 로 올려 두면 `t[sz + i] = a[i]` 로 딱 떨어진다.
`n = 8` 이면 `sz = 8`, 트리 배열 크기는 `2 × 8 = 16`.

`n` 이 2의 거듭제곱이 아니면 남는 리프는 **0으로 채운다.** 합에 0을 더해도 값이 안 변하니 안전하다.

### 2단계 — build: 아래에서 위로 한 번

```cpp
for (int i = 0; i < n; i++) t[sz + i] = a[i];   // 리프
for (int i = sz - 1; i >= 1; i--)               // 내부 노드
    t[i] = t[2*i] + t[2*i + 1];
```

`i` 를 **큰 쪽에서 작은 쪽으로** 훑는 게 요령이다. 자식(`2i`, `2i+1`)의 번호가 `i` 보다 크므로,
자식이 항상 먼저 계산돼 있다.

노드가 `2·sz - 1` 개고 각각 덧셈 한 번이니 **build 는 O(n)** 이다.

### 3단계 — query: 아래에서 위로 올라가며 줍는다

리프 인덱스로 옮긴 뒤(`l += sz, r += sz`), 매 레벨에서 이렇게 한다.

```cpp
if (l & 1) res += t[l++];   // l 이 홀수 = 오른쪽 자식
if (r & 1) res += t[--r];   // r 이 홀수 = 오른쪽 자식
l >>= 1; r >>= 1;           // 한 레벨 위로
```

**왜 홀수(오른쪽 자식)일 때만 줍는가?**

`l` 이 짝수면 왼쪽 자식이다. 그러면 그 부모가 `[l, l+2)` 를 통째로 담고 있으니
지금 줍지 말고 한 레벨 올라가서 부모를 보면 된다.

`l` 이 홀수면 오른쪽 자식이다. 부모에는 **구간 밖인 왼쪽 형제**도 섞여 있으니
부모를 쓸 수 없다. **지금 이 노드를 확정하고 오른쪽으로 한 칸 비켜야** 한다.

### 4단계 — update: 리프에서 루트까지

```cpp
i += sz; t[i] = v;
for (i >>= 1; i >= 1; i >>= 1)
    t[i] = t[2*i] + t[2*i + 1];
```

경로 길이가 곧 트리 높이 `log₂ sz` 다.

## 코드로 옮기기

```cpp
int sz;
vector<long long> t;             // t[1] = 루트, t[sz + i] = a[i]

void build(vector<int>& a) {
    sz = 1;
    while (sz < a.size()) sz <<= 1;          // ← 1단계: 2의 거듭제곱으로 올림
    t.assign(2 * sz, 0);                     // ← 남는 리프는 0(합의 항등원)
    for (int i = 0; i < a.size(); i++)
        t[sz + i] = a[i];
    for (int i = sz - 1; i >= 1; i--)
        t[i] = t[2*i] + t[2*i + 1];          // ← 2단계
}

long long query(int l, int r) {              // [l, r) 반열린 구간
    long long res = 0;
    for (l += sz, r += sz; l < r; l >>= 1, r >>= 1) {
        if (l & 1) res += t[l++];            // ← 3단계
        if (r & 1) res += t[--r];
    }
    return res;
}

void update(int i, int v) {
    i += sz;
    t[i] = v;
    for (i >>= 1; i >= 1; i >>= 1)
        t[i] = t[2*i] + t[2*i + 1];          // ← 4단계
}
```

| | 시간 |
|---|---|
| build | O(n) |
| query | O(log n) |
| update | O(log n) |

앞의 방법 A·B와 달리 **둘 다 로그**다.

## 자주 하는 실수

**닫힌 구간과 반열린 구간을 섞는다.** ★ 이 자료구조 최대의 버그 원인이다.
이 코드는 `[l, r)` 반열린 구간이다. 반복 버전은 반열린이 압도적으로 편하고
(`l < r` 로 끝나고 `r++` 이 없다), 재귀 버전은 닫힌 `[l, r]` 이 관례다.
**한 관례를 정하고 끝까지 밀고 가자.**

**남는 리프에 잘못된 값을 채운다.** 합이면 0이 맞지만, **최솟값 트리라면 `INT_MAX`** 를 넣어야 한다.
0을 넣으면 답이 전부 0이 된다. 채워야 하는 건 그 연산의 **항등원**이다.

**`int` 오버플로.** `n = 10⁵`, 값이 `10⁹` 이면 합이 `10¹⁴` 다. `long long` 을 쓰자.

**build 를 update 로 대신한다.** 원소를 하나씩 `update` 로 넣으면 `O(n log n)` 이다.
아래에서 위로 한 번 훑으면 `O(n)` 이다.

## 스스로 확인하기

1. **build 단계**를 넘겨 보자. 리프가 채워진 뒤 내부 노드가 **아래에서 위로** 계산된다.
2. **query 단계**에서 초록으로 남는 노드를 세어 보자. 구간이 6칸인데 노드는 4개뿐이다.
   레벨마다 **최대 2개**만 채택되는 것을 확인해 보자.
3. **update 단계**를 보자. `a[4]` 를 바꾸면 흰색으로 강조되는 노드가 리프에서 루트까지
   **한 줄**뿐이다. 나머지는 건드리지 않는다.
4. **갱신 후 같은 구간을 다시 질의**한다. 답이 달라지는 것을 확인해 보자.
5. 입력 길이를 5나 6으로 바꿔 보자. `sz` 가 8로 올라가고 남는 리프가 0으로 채워진다.

아래 **깊이 보기**에서는 query 가 구간을 정확히 분해한다는 것을 불변식으로 증명하고,
합 말고 어떤 연산까지 얹을 수 있는지(**모노이드**) 다룬다.
