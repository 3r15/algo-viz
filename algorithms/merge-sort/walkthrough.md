## 어떤 문제인가

[버블 정렬](#/algo/bubble-sort)과 [삽입 정렬](#/algo/insertion-sort)은 원소 6개 정도는 잘 다루지만,
10만 개가 되면 감당하지 못한다. 비교 횟수가 `n²` 에 비례해서 늘기 때문이다.

```
n = 100      →  약 5,000 번
n = 100,000  →  약 5,000,000,000 번   ← 50억
```

더 좋은 방법이 필요하다. 출발점은 이 관찰이다.

> **정렬된 두 배열을 하나로 합치는 건 아주 쉽다.**

## 손으로 해보기

### 먼저 "합치기"만 해 보자

정렬된 두 묶음이 있다고 하자.

```
왼쪽:  [2, 5, 9]
오른쪽: [1, 5, 6]
```

두 묶음의 **맨 앞만** 보면서 작은 쪽을 꺼내 결과에 붙인다.
꺼낸 쪽만 손가락을 한 칸 옮긴다.

```
왼 [2 5 9]   오 [1 5 6]   결과 []
    ↑            ↑
2 vs 1 → 1 이 작다 → 1 을 꺼낸다

왼 [2 5 9]   오 [1 5 6]   결과 [1]
    ↑              ↑
2 vs 5 → 2 를 꺼낸다

왼 [2 5 9]   오 [1 5 6]   결과 [1 2]
      ↑            ↑
5 vs 5 → 같다! 왼쪽을 먼저 꺼낸다

왼 [2 5 9]   오 [1 5 6]   결과 [1 2 5]
        ↑          ↑
9 vs 5 → 5 를 꺼낸다

왼 [2 5 9]   오 [1 5 6]   결과 [1 2 5 5]
        ↑            ↑
9 vs 6 → 6 을 꺼낸다

오른쪽이 비었다 → 왼쪽에 남은 9 를 그대로 붙인다
결과 [1 2 5 5 6 9]
```

**한 번에 한 개씩만 꺼내고, 각 원소를 딱 한 번씩만 본다.**
그래서 합치기는 두 묶음 크기의 합에 비례하는 시간, 즉 O(n) 이다.

> 5와 5가 같을 때 **왼쪽을 먼저 꺼낸 것**을 기억해 두자. 이 사소해 보이는 선택이
> "같은 값의 원래 순서를 지킨다"(안정성)를 만든다.

### 이제 전체를 정렬해 보자

합치기가 쉽다는 걸 알았으니, **정렬된 두 묶음을 어떻게 만들 것인가**만 남았다.
답은 조금 뻔뻔하다 — **같은 방법으로 만든다.**

`[5, 2, 9, 1, 5, 6]` 을 반씩 쪼개 내려간다.

```
        [5 2 9 | 1 5 6]
        /             \
   [5 2 9]           [1 5 6]
   /     \           /     \
 [5 2]   [9]      [1 5]    [6]
 /   \            /   \
[5]  [2]        [1]   [5]
```

원소가 하나면 그건 이미 정렬된 것이다. 여기서부터 **거꾸로 합쳐 올라온다.**

```
[5] [2]      → [2 5]
[2 5] [9]    → [2 5 9]
[1] [5]      → [1 5]
[1 5] [6]    → [1 5 6]
[2 5 9] [1 5 6] → [1 2 5 5 6 9]      ← 위에서 손으로 해 본 그 합치기
```

## 아이디어 쌓기

### 1단계 — 합치기는 싸다

정렬된 두 배열을 합치는 데 O(n). 이게 유일한 무기다.

### 2단계 — 재료를 어디서 구하나

"정렬된 두 배열"이 필요한데, 그걸 만드는 게 원래 문제다. 순환처럼 보이지만 빠져나갈 구멍이 있다.

> **크기 1짜리 배열은 이미 정렬돼 있다.**

이걸 바닥으로 삼아, 크기 1 → 2 → 4 → … 로 올라가면 된다.

### 3단계 — 자기 자신을 부른다

"절반을 정렬한다"를 **같은 함수를 다시 부르는 것**으로 표현한다.

```
mergeSort(구간):
    구간이 1칸 이하면 → 이미 정렬됨, 그냥 돌아간다     ← 바닥
    아니면:
        왼쪽 절반을 mergeSort
        오른쪽 절반을 mergeSort
        둘을 합친다
```

이렇게 자기를 부르는 것을 **재귀**라고 한다. "쪼개다 보면 언젠가 1칸이 된다"는 것이
무한히 돌지 않는 이유다.

### 4단계 — 왜 빨라지나

쪼개는 깊이를 세어 보자. 6개를 반으로 계속 나누면 `6 → 3 → 1.5 → …` 로
약 `log₂ 6 ≈ 3` 단계 만에 1칸이 된다.

각 깊이에서 합치기에 드는 총 시간은 그 층의 원소 수 합, 즉 `n` 이다.

```
깊이 0:  [6칸] 하나를 합침                → 6
깊이 1:  [3칸] 두 개를 합침               → 6
깊이 2:  [1~2칸] 여러 개를 합침           → 6
                                   총 6 × 3 = 18
```

**깊이 `log n` × 층마다 `n` = `n log n`.**

`n = 100,000` 이면 `100,000 × 17 ≈ 170만` 번이다. 50억과 비교해 보자.

## 코드로 옮기기

```cpp
void mergeSort(vector<int>& a, int lo, int hi) {
    if (lo >= hi) return;                 // ← 바닥: 0~1칸이면 이미 정렬됨
    int mid = (lo + hi) / 2;
    mergeSort(a, lo, mid);                // ← 왼쪽 절반
    mergeSort(a, mid + 1, hi);            // ← 오른쪽 절반
    merge(a, lo, mid, hi);                // ← 합치기
}
```

세 줄이 3단계에서 말로 쓴 것과 정확히 일치한다.

```cpp
void merge(vector<int>& a, int lo, int mid, int hi) {
    vector<int> tmp;
    int i = lo, j = mid + 1;                            // 두 손가락
    while (i <= mid && j <= hi)                         // 둘 다 남아 있는 동안
        tmp.push_back(a[i] <= a[j] ? a[i++] : a[j++]);  // 작은 쪽을 꺼낸다
    while (i <= mid) tmp.push_back(a[i++]);             // 왼쪽 남은 것
    while (j <= hi)  tmp.push_back(a[j++]);             // 오른쪽 남은 것
    for (int k = 0; k < tmp.size(); k++)
        a[lo + k] = tmp[k];                             // 원래 자리에 되돌린다
}
```

| 줄 | 손으로 한 것 중 무엇 |
|---|---|
| `int i = lo, j = mid + 1` | 두 묶음의 맨 앞에 손가락을 둔다 |
| `a[i] <= a[j] ? ... : ...` | 작은 쪽을 꺼내고 그 손가락만 전진 |
| `while (i <= mid)` | 한쪽이 먼저 바닥나면 나머지를 그대로 |
| `a[lo + k] = tmp[k]` | 임시 공간의 결과를 원래 배열에 옮김 |

**`<=` 가 안정성의 핵심이다.** 값이 같으면 왼쪽(=원래 앞쪽)을 먼저 꺼낸다.
`<` 로 바꾸면 오른쪽이 먼저 나와 순서가 뒤집힌다.

## 자주 하는 실수

**`tmp` 없이 제자리에서 합치려 한다.** 값을 덮어쓰다 원본이 사라진다.
합치기는 O(n) 추가 공간이 필요하고, 그게 이 알고리즘이 치르는 대가다.

**`mid` 를 잘못 잡는다.** `mergeSort(a, lo, mid)` 와 `mergeSort(a, mid+1, hi)` 에서
`+1` 을 빠뜨리면 오른쪽 구간이 줄어들지 않아 **무한 재귀**에 빠진다.

**`lo >= hi` 를 `lo == hi` 로 쓴다.** 빈 구간(`lo > hi`)이 들어올 때 걸러지지 않는다.

**`tmp` 를 매번 새로 만든다.** 재귀 호출마다 벡터를 할당하면 느려진다.
실전에서는 크기 `n` 짜리 버퍼를 한 번만 잡아 돌려쓴다.

## 스스로 확인하기

1. 스텝을 넘기며 **깊이가 깊어졌다가 얕아지는 리듬**을 느껴 보자.
   왼쪽 끝까지 파고들었다가 합치며 올라오고, 다시 오른쪽으로 내려간다.
2. **`1 2 3 4 5 6` 을 넣어 보자.** 이미 정렬돼 있어도 스텝 수가 거의 같다.
   병합 정렬은 입력에 상관없이 항상 같은 일을 한다 — 최악이 없는 대신 최선도 없다.
3. 같은 입력을 [퀵 정렬](#/algo/quick-sort)에 넣어 보자. 퀵 정렬은 이 입력에서
   오히려 스텝이 폭증한다(최악의 피벗 선택).
4. 값이 같은 입력에서 두 개의 5가 서로 넘어가지 않는지 확인해 보자.

아래 **깊이 보기**에서는 합치기가 왜 옳은지 불변식으로 증명하고,
**어떤 비교 기반 정렬도 `n log n` 보다 빠를 수 없다**는 하한을 다룬다.
