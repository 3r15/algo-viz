## 어떤 문제인가

[다익스트라](#/algo/dijkstra)는 시작점에서 **모든** 정점까지의 최단 거리를 구한다.
그런데 우리가 알고 싶은 게 **딱 한 곳까지의 길**이라면?

서울에서 부산까지 가는 길을 찾는데, 다익스트라는 인천·춘천·대전을 골고루 탐색한다.
사람이라면 **일단 남쪽으로** 가 볼 텐데 말이다.

> 목적지가 정해져 있다면, **"목적지 쪽으로 보이는 방향"을 먼저 탐색**하면 안 될까?

이 아이디어가 **A\*(에이 스타)** 다.

## 손으로 해보기

### 두 가지 숫자

각 정점에 숫자를 **두 개** 붙인다.

```
g(v)  시작점에서 v 까지 실제로 든 비용    ← 다익스트라의 dist 와 같다
h(v)  v 에서 목표까지 남은 비용의 "추정치"  ← 새로 추가된 것
```

그리고 둘을 더한 값으로 우선순위를 매긴다.

```
f(v) = g(v) + h(v)
     = 여기까지 온 비용 + 여기서 목표까지 갈 것 같은 비용
     = 이 정점을 거치는 전체 여정의 예상 비용
```

다익스트라는 `g` 로 줄을 세우고, A\* 는 **`f` 로 줄을 세운다.** 그게 전부다.

### `h` 는 어디서 오나

이 페이지는 정점에 좌표가 있으니 **목표까지의 직선 거리**를 쓴다.
실제 길은 구불구불하니 직선 거리는 항상 실제보다 **작거나 같다.**
이 성질이 나중에 아주 중요해진다.

### 따라가 보기

기본 그래프에서 시작 `0`, 목표 `7`. 정점 `6` 은 목표 반대편의 막다른 골목이다.

```
        1 ── 3
       /  \    \
      0    \    7 (목표)
     / \    4    /
    6   2 ─┘  \ /
 (막다른)      5
```

`h` 값(목표에서 먼 정점일수록 크다):

```
h[0]=7.2  h[1]=5.4  h[2]=5.5  h[3]=3.1  h[4]=3.3  h[5]=2.4  h[6]=7.5  h[7]=0
```

```
① 0 을 꺼낸다 (f = 0 + 7.2 = 7.2)
   0→1(3): g[1]=3, f = 3 + 5.4 = 8.4
   0→2(3): g[2]=3, f = 3 + 5.5 = 8.5
   0→6(3): g[6]=3, f = 3 + 7.5 = 10.5   ← f 가 크다! 뒤로 밀린다
   열린 목록: 8.4:1  8.5:2  10.5:6

② 1 을 꺼낸다 (f = 8.4 — 가장 작다)
   1→3(3): g[3]=6, f = 6 + 3.1 = 9.1
   열린 목록: 8.5:2  9.1:3  10.5:6

③ 2 를 꺼낸다 (f = 8.5)
   2→4(3): g[4]=6, f = 6 + 3.3 = 9.3
   열린 목록: 9.1:3  9.3:4  10.5:6

④ 3 을 꺼낸다 (f = 9.1)
   3→7(4): g[7]=10, f = 10 + 0 = 10.0
   열린 목록: 9.3:4  10.0:7  10.5:6

⑤ 4 를 꺼낸다 (f = 9.3)
   4→5(2): g[5]=8, f = 8 + 2.4 = 10.4
   열린 목록: 10.0:7  10.4:5  10.5:6

⑥ 7 을 꺼낸다 (f = 10.0)  → 목표다! 끝.
```

**정점 6은 끝내 확장되지 않았다.** `f = 10.5` 로 밀려 있다가 목표(10.0)가 먼저 나왔기 때문이다.

같은 그래프를 다익스트라로 돌리면 어떻게 될까? `g[6] = 3` 이 가장 작으므로
**두 번째로 6을 확장한다.** 목표와 정반대 방향인데도 말이다.

```
확장한 정점 수:   A* → 5개      다익스트라 → 8개
```

## 아이디어 쌓기

### 1단계 — `h ≡ 0` 이면 다익스트라다

`h` 를 전부 0으로 두면 `f = g` 가 되어 정확히 다익스트라가 된다.
**A\* 는 다익스트라의 일반화**다. 새로 배우는 게 아니라 하나를 얹는 것이다.

### 2단계 — `h` 는 절대 과대평가하면 안 된다 ★

`h` 가 실제 남은 비용보다 **크면** 어떻게 될까?

목표로 가는 진짜 최단 경로 위의 정점에게 "너는 아직 멀었어"라고 잘못 말하는 셈이다.
그러면 그 정점이 뒤로 밀리고, 엉뚱한 길이 먼저 목표에 도달해 **틀린 답**이 나온다.

> `h(v) ≤ (v 에서 목표까지의 진짜 최단 비용)`
>
> 이 조건을 만족하는 `h` 를 **허용 가능(admissible)** 하다고 한다.

직선 거리가 좋은 `h` 인 이유가 이것이다 — 실제 길은 직선보다 짧을 수 없으니까.

### 3단계 — 단위를 맞춰야 한다

여기 함정이 하나 있다. 좌표 거리와 간선 비용은 **단위가 다르다.**
화면상 거리 24만큼 떨어진 두 점을 잇는 간선의 비용이 3일 수도 있다.
직선 거리 24를 그대로 `h` 로 쓰면 엄청난 과대평가다.

그래서 축척을 하나 곱한다.

```
scale = 모든 간선에 대해 min( 간선 비용 / 그 간선의 직선 길이 )
      = "직선 거리 1 만큼 움직이는 데 드는 최소 비용"

h(v) = (v 에서 목표까지의 직선 거리) × scale
```

이러면 어떤 경로든 `직선 길이 × scale` 이상의 비용이 드니 `h` 가 절대 초과하지 않는다.

### 4단계 — 목표를 "꺼낼 때" 멈춘다

목표를 열린 목록에 **넣을 때** 멈추면 안 된다. 그 시점엔 더 짧은 경로가 아직 발견되지 않았을 수 있다.
**꺼낼 때** 비로소 "이보다 싼 길은 없다"가 보장된다.

## 코드로 옮기기

```cpp
void aStar(vector<vector<pair<int,int>>>& adj, int s, int goal) {
    vector<double> g(adj.size(), INF);
    priority_queue<pair<double,int>, vector<pair<double,int>>,
                   greater<>> open;         // ← (f, 정점) 최소 힙
    g[s] = 0;
    open.push({h(s), s});                   // ← g=0 이므로 f = h(s)
    while (!open.empty()) {
        auto [f, u] = open.top(); open.pop();
        if (u == goal) return;              // ← 4단계: 꺼낼 때 종료
        if (f > g[u] + h(u)) continue;      // ← 낡은 항목(다익스트라와 동일)
        for (auto [v, w] : adj[u]) {
            if (g[u] + w < g[v]) {          // ← 완화도 다익스트라와 동일
                g[v] = g[u] + w;
                open.push({g[v] + h(v), v}); // ← 차이는 여기뿐: f = g + h
            }
        }
    }
}
```

[다익스트라 코드](#/algo/dijkstra)와 나란히 놓으면 **딱 세 군데**가 다르다.

| | 다익스트라 | A\* |
|---|---|---|
| 큐에 넣는 값 | `dist[v]` | `g[v] + h(v)` |
| 종료 | 큐가 빌 때까지 | 목표를 꺼내면 |
| 준비물 | — | `h` 함수 |

## 자주 하는 실수

**`h` 가 과대평가한다.** 2단계의 그 문제. 답이 최단이 아니게 된다.
격자에서 상하좌우만 이동하는데 유클리드 거리를 쓰면 과소평가라 안전하지만,
대각선 이동이 없는데 대각선 거리를 쓰면 위험하다.

**격자에서 맨해튼 거리를 안 쓴다.** 상하좌우만 움직인다면 `|dx| + |dy|` 가 정확한 하한이자
가장 강한 `h` 다. 유클리드 거리는 허용 가능하지만 **약해서** 손해다.

**목표를 넣을 때 멈춘다.** 4단계의 그 문제.

**단위를 안 맞춘다.** 3단계의 축척 이야기. `h` 와 간선 비용의 단위가 다르면
아무리 좋은 아이디어도 소용없다.

**`h` 가 좋으면 최악도 빨라진다고 생각한다.** 아니다. `h` 가 아무 정보를 못 주면
다익스트라와 똑같이 전부 훑는다. **최악은 나아지지 않는다.**

## 스스로 확인하기

1. **정점 라벨이 `g+h` 형태**다. 예를 들어 `3+5.4` 는 `g=3, h=5.4, f=8.4` 라는 뜻이다.
2. **`PQ` 표시**를 보자. `f` 값 순서로 정렬돼 있다.
3. **정점 6을 주목하자.** 발견은 되지만(테두리 강조) 끝까지 확장되지 않는다.
   `h[6]` 이 커서 `f` 가 밀렸기 때문이다.
4. 같은 그래프를 [다익스트라](#/algo/dijkstra)에 넣어 보자. 6을 확장하는지 확인해 보자.
5. 편집기에서 **가중치를 이상하게 바꿔 보자.** 예를 들어 `0-6` 을 1로 낮추면
   `scale` 이 작아져 `h` 가 전체적으로 약해지고, A\* 가 다익스트라에 가까워진다.
   이게 3단계에서 말한 축척의 영향이다.

아래 **깊이 보기**에서는 "허용 가능하면 최적"을 증명하고,
더 강한 조건인 **일관성(consistency)** 이 왜 필요한지 다룬다.
